# CORTEX 平台 — 客戶資料保密控制說明（已實作機制）

> 對象：外部客戶資安稽核
> 範圍：本文件僅陳述「目前程式碼已實作並運行中」的保密 / 存取控制機制；所有敘述均可對照原始碼驗證。
> 撰寫日期：2026-06-11

---

## 0. 防護分層總覽

CORTEX 對客戶機密資料（訂單 / 採購 / BOM / 生產資訊）的保護，依資料生命週期分為四層，並在每一層都有已落地的技術控制：

| 層 | 控制目的 | 已實作的主要控制 |
|----|---------|----------------|
| **L1 身分與存取** | 確認「誰能進入」 | LDAP/AD 驗證、OIDC SSO、不透明 Token + 伺服器端 Session、角色／組織自動綁定、外網強制 MFA、即時強制登出 |
| **L2 資料可見範圍** | 限制「看得到哪些資料」 | 資料政策（使用者／角色／類別多層）、Oracle Multi-Org 組織範圍解析、知識庫機密旗標與多層級分享、AI 戰情 / 排程任務分級分享 |
| **L3 處理與外送** | 控制「送去哪、金鑰怎麼護」 | LLM 供應商路由（Gemini / Azure OpenAI）、API 金鑰 AES-256-GCM 加密、MCP 下游身分 JWT 簽發、ERP 連線層唯讀強制 |
| **L4 稽核與留存** | 確保「留痕、可追、定期清」 | 對話敏感字偵測與管理員通知、認證事件稽核、API/MCP/ERP 呼叫稽核、分層資料保留與自動清理 |

## 1. L1 — 身分認證與存取控制

### 1.1 多來源身分驗證
- **LDAP / AD 整合**：支援企業 AD 帳號登入。對 username 施加白名單正則（`^[A-Za-z0-9._\-@]{1,64}$`）並對 LDAP filter 特殊字元做 RFC 4515 escape，防止 LDAP 注入。
- **OIDC 單一登入（SSO）**：採 authorization code flow；以 `state` 參數搭配 Redis one-shot key（300 秒 TTL，使用即刪）防止 CSRF；`redirect_uri` 動態判斷並比對允許清單，支援內外網並存。
- **密碼儲存**：本地帳號密碼以 **bcrypt（cost 12）** 雜湊儲存，並以 `password_hashed` 旗標標示；系統啟動時會批次將既有明文密碼雜湊化。

### 1.2 Session 與 Token
- 採 **不透明（opaque）UUID Bearer Token + 伺服器端 Session**（非自包含 JWT）。Token 本身僅為隨機 UUID、不攜帶任何身分資訊；使用者身分、角色、組織屬性等全部存放於伺服器端 Session record，用戶端無法竄改。
- Session 以 **Redis** 集中儲存（多節點共享），Token 有效期 8 小時並採滑動過期（每次請求重置 TTL）。

### 1.3 角色與組織自動綁定
- 使用者於 SSO / LDAP 首次登入時，若具備員工工號且 ERP 已設定，系統自動從 Oracle ERP 同步其組織屬性：**部門代碼、利潤／成本中心、事業處、事業群、廠別**。
- 依 `role_org_bindings` 表，按「部門 → 成本中心 → 事業處 → 事業群」優先序自動解析並指派角色；查無綁定則退回預設角色。
- 角色定義各項功能權限（文件／音訊／圖片上傳、排程任務、技能建立、知識庫建立等），**並支援個人層級覆寫**（個人設定優先於角色預設）。

### 1.4 權限邊界與管理端隔離
- 管理專用 API（使用者管理、角色、資料政策、LLM 模型、敏感字、稽核查詢等）以雙層中介軟體 `verifyToken` + `verifyAdmin` 強制把關，非管理員一律 403。

### 1.5 帳號生命週期
- 本地登入路徑檢查帳號 `status`（停用即拒登）、生效日 / 失效日。
- 管理員可對指定使用者**強制登出**：系統掃描所有 Session 並刪除該使用者的全部 Token，使其下一次 API 呼叫即被踢回登入頁（適用離職 / 權限調整即時生效）。

### 1.6 外網存取強化
- 內外網以 CIDR 判定分流；可設定 internal-only 路徑（外網命中即 403）與外網 IP 白名單。
- **外網登入強制多因素認證（MFA）**：透過 Webex 私訊與 Email 並行發送一次性驗證碼（OTP），任一通道驗證成功才放行；支援受信裝置（30 天）以平衡安全與便利。
- 外網登入端點具備 per-IP 速率限制。

## 2. L2 — 資料可見範圍隔離

> 本層回答客戶最關心的問題：**「不同事業單位 / 部門的人，能不能看到不該看的訂單、採購、BOM 資料？」**

### 2.1 資料政策（Data Policy）
- 系統以 6 張資料表（`ai_data_policies` / `ai_data_policy_rules` / `ai_user_policies` / `ai_role_policies` / `ai_user_cat_policies` / `ai_role_cat_policies`）儲存與管理分層存取政策。
- 政策解析採**短路式優先序**：使用者×類別 → 角色×類別 → 使用者一般 → 角色一般，上層命中即套用、不被下層覆寫；上兩層在查詢綁定政策類別時觸發。
- 政策規則支援 `include` / `exclude` 條件，依利潤中心、組織別等維度限定可查資料範圍；並可設定 **完全封鎖（full_block）** 政策，非管理員命中即無條件拒絕查詢（第 1/2 層）。

### 2.2 資料政策的執行方式（誠實揭露機制邊界）
CORTEX 對 AI 戰情（自然語言查 ERP）查詢，採**多道並行的資料範圍控制**：

1. **連線層唯讀強制（硬性）**：所有對 ERP 的查詢都經唯讀連線代理（`ReadOnlyConnectionProxy`），於連線層強制 SQL 必須以 `SELECT` / `WITH` 開頭，封鎖任何 DML/DDL、`FOR UPDATE` 與多語句串接——此為程式層的確定性保證，無法繞過。
2. **越權詞偵測（硬性攔截）**：使用者提問若提及其權限範圍外的組織代碼 / OU / SOB 名稱，系統在產生 SQL **之前**即偵測並拒絕該次查詢。
3. **Oracle Multi-Org 範圍過濾**：依使用者政策解析出其可見的 organization / operating unit / set-of-books 範圍，於 dashboard 查詢注入 `IN (...)` 條件；無任何可見範圍時降為零結果（`1=0`），ERP 無法連線時整體阻擋查詢。
4. **政策條件導入查詢生成**：已解析的資料權限 WHERE 條件，會以明確指示形式寫入 AI 的查詢生成提示，要求其產生的 SQL 納入該過濾條件。

> 說明：上述第 1～3 項為程式層強制控制；第 4 項（一般資料政策的列篩選）係以「指示查詢生成」方式實現，並非對 AI 產出 SQL 的事後改寫。實務部署時建議搭配資料政策對「使用者可存取的 ERP 帳號 / Schema 範圍」於來源端再做一道最小權限限制，形成縱深防禦。

### 2.3 知識庫（KB）權限與機密旗標
- 知識庫透過 `kb_access` 表進行**多層級分享**：可按使用者、角色、部門、利潤中心、事業處、廠別、事業群授權，權限分 **`use`（檢索查詢）** 與 **`edit`（編輯／上傳）** 兩級。
- **機密知識庫（`is_confidential=1`）**：
  - 即使是系統管理員，對機密 KB **也只能看到清單 metadata、拿不到內容 / 文件 / 檢索片段**，除非其本人為建立者或在 `kb_access` 被明確授權。
  - 機密與公開狀態互斥（標記機密時自動取消公開）。
- **檢索前必驗權**：KB 搜尋端點在執行檢索前先驗證使用者對該 KB 的存取權；無權者根本不會讓該 KB 進入可被 AI 呼叫的工具清單，因此即使在對話情境也無法被誘導讀出無權 KB 的內容。
- **外部 API 金鑰存取 KB**：可設定可存取 KB 白名單與 `allow_confidential` 旗標；機密 KB 預設拒絕 API 存取，須明確開啟才可。寫入類操作的 API 金鑰必須綁定一個真實使用者（acts-as-user），權限與配額沿用該使用者既有規則，無法繞過。

### 2.4 AI 戰情 / 專案 / 排程任務 — 分級分享
- **專案層**：支援 `use` / `develop` 兩級分享，對應 7 種收贈者型別（使用者、角色、部門、成本中心、事業處、廠別、事業群），僅擁有者 / 管理員可管理。
- **專案公開**：須由管理員核准（`public_approved`）後才生效。
- **排程任務分享**：`use`（檢視執行紀錄、下載產出）/ `develop`（修改設定、立即執行）兩級。**核心保證：排程任務的執行身分永遠等於任務擁有者（owner）**，即使 develop 受贈者修改了內容，仍以 owner 的權限執行，不會藉此提權。含資料寫入 / 知識庫寫入 / 告警等危險節點的任務，**禁止 develop 級分享**。
- 所有分享記錄授予者與時間戳，可供稽核。

## 3. L3 — LLM 資料外送邊界與金鑰保護

### 3.1 供應商路由
- 平台支援 **Google Gemini（經 Google Cloud Vertex AI）** 與 **Azure OpenAI** 兩種 LLM 供應商，依模型設定的 `provider_type` 於對話路徑分流。
- 生產環境預設文字生成與向量化均走 **Vertex AI**（企業級 GCP 環境）。

> 商務層說明（非程式控制）：是否使用各供應商的企業級資料保護條款（不用於模型訓練、零資料留存 / no-logging、資料駐地等），屬與 Google / Microsoft 的合約範疇，建議於合約附件中對客戶提供書面條款。本平台程式層不對外送內容做駐地強制，資料駐地以 GCP / Azure 專案設定為準。

### 3.2 金鑰保護
- 所有在資料庫中儲存的 LLM API 金鑰，均以 **AES-256-GCM 加密**（含完整性驗證標籤）儲存於 `api_key_enc` 欄位；主加密金鑰由環境變數注入（`LLM_KEY_SECRET`）。
- Azure OpenAI 模型在主對話路徑使用各自獨立的加密金鑰；Gemini 主對話於生產環境採 Vertex AI service account 憑證。
- 金鑰管理端點僅限管理員；查詢時只回傳「是否已設定金鑰」旗標，不回傳金鑰明文。
- 建議生產環境以 Kubernetes Secret / Vault 注入 `LLM_KEY_SECRET` 與服務帳號憑證。

### 3.3 內部推理不外洩
- 對 Gemini 3.x 的「思考（extended thinking）」段落，系統自動過濾，僅回傳最終答案，內部推理過程不會出現在使用者回應中。

### 3.4 下游系統的使用者身分驗證（MCP）
- 當 MCP 工具伺服器啟用 `send_user_token` 時，CORTEX 為每次呼叫簽發一枚 **RS256 JWT**（`X-User-Token`），內含使用者工號 / email / 部門，**有效期 5 分鐘、帶 `jti` 防重放**。下游系統可用公鑰驗證簽名與有效期，自行對「真實使用者」做授權，而非盲信閘道。私鑰僅 CORTEX 持有。

## 4. L4 — 稽核、敏感字偵測與資料保留

### 4.1 對話敏感字偵測與通知
- 管理員可維護敏感詞清單（支援單筆新增、CSV 批次匯入、刪除）。
- 每次使用者送出對話訊息後，系統掃描其輸入文字；命中時寫入稽核表（標記 `has_sensitive`、記下命中詞），並**非同步寄送 Email 通知管理員**（含使用者、工號、Session、命中詞與訊息內容），通知狀態回填。
- 來源涵蓋網頁對話與 Webex Bot，稽核紀錄標記來源（web / webex）。

> 機制定位（誠實揭露）：此為「**偵測 → 記錄 → 通知**」的事後稽核機制，協助管理員掌握敏感資訊流向；非即時阻斷使用者送出。

### 4.2 多面向稽核軌跡
- **認證事件稽核（`auth_audit_logs`）**：登入成功 / 失敗、MFA 挑戰、IP 信任等事件，記錄事件類型、IP、User-Agent、結果、錯誤訊息與 metadata，並提供管理端查詢與指定 IP 行為彙整。
- **外部 API 呼叫稽核（`api_key_usage_log`）**：凡通過 API 金鑰認證的外部請求，記錄端點、方法、狀態碼、代理使用者、來源 IP、操作資源、token 用量與耗時；KB 擁有者可查詢「過去 N 天誰透過哪把金鑰存取了該 KB」。
- **MCP 工具呼叫稽核（`mcp_call_logs`）**：記錄伺服器、工具名稱、參數、回應預覽、狀態、耗時，並關聯使用者 email 與 JWT `jti`。
- **ERP 工具執行稽核（`erp_tool_audit_log`）**：對進入 ERP 連線並執行的呼叫，記錄工具、使用者、Session、觸發來源、存取模式、輸入 / 輸出取樣、耗時、回傳列數與錯誤碼。
- **使用量歸屬**：每次對話完成後將「使用者 + 模型 + token 量」寫入 `token_usage`，管理端可依使用者 / 模型回溯。

### 4.3 資料保留與自動清理
系統以每日排程依下列分層政策自動清理（天數均可由管理設定調整）：

| 資料類別 | 預設保留 |
|---------|---------|
| 一般稽核日誌 | 90 天 |
| **含敏感詞稽核日誌** | **365 天**（合規長期追溯） |
| 對話 Session 與訊息 | 90 天 |
| 上傳會話檔（暫存產出） | 7 天 |
| Token 使用紀錄 | 365 天 |
| API 金鑰使用日誌 | 90 天 |

## 5. ERP / 工具呼叫的權限與防護（L2 / L3 補充）

CORTEX 可讓 AI 透過受控工具查詢 ERP，對此設有多重防護：

- **唯讀強制**：見 §2.2 第 1 項，ERP 查詢於連線層強制唯讀。
- **參數綁定變數防 SQL 注入**：所有工具參數值一律以 Oracle 綁定變數（bind variable）傳入 PL/SQL，使用者或 AI 提供的參數值**不會被字串串接進 SQL**，杜絕經由參數值的 SQL 注入。
- **數值 / 日期型別強制**：數值與日期型參數於執行前做格式驗證，不合法即拒絕。
- **LOV 解析**：支援以易讀代碼 / 名稱輸入，自動轉換為內部 ID；多筆符合時列舉候選要求精確輸入，避免歧義誤操作。
- **手動執行的存取權驗證**：透過 REST 端點手動執行 ERP 工具時，以 `skill_access` 表進行多屬性（使用者 / 角色 / 部門 / 廠別 / 事業處 / 事業群等）存取權比對，擋下無權使用者。
- **寫入操作的人工確認**：可將工具設定為需確認，由 AI 觸發的寫入會回傳「待確認」並停手，須使用者帶確認 token（5 分鐘有效、用後即刪、防重放）手動執行；亦提供 dry-run（SAVEPOINT/ROLLBACK 包裹）供驗證參數。

## 6. 部署與基礎設施

- **集中式 Session（Redis）**：多節點共享，支援強制登出即時生效。
- **傳輸加密**：對外經 TLS 終結（WAF / Ingress）。
- **稽核集中化**：K8s 環境集中蒐集應用日誌（Loki）。
- **健康監控**：容器健康檢查與可用性監控（Uptime Kuma）。
